# บทที่ 5 สรุป อภิปรายผล และข้อเสนอแนะ

> เขียนหลังบทที่ 4 เสร็จ ทุกข้อสรุปต้องย้อนกลับไปที่**วัตถุประสงค์ 4 ข้อในบทที่ 1** และตัวเลขในบทที่ 4

## 5.1 สรุปผลการดำเนินงาน

ตอบวัตถุประสงค์ทีละข้อ:

| วัตถุประสงค์ (บทที่ 1) | ผลที่ได้ | หลักฐาน |
|---|---|---|
| 1. คลังเอกสารจัดตามภาค → รุ่น → วิชา ค้นด้วยรหัสวิชาข้ามรุ่น | **[เติม]** | หัวข้อ 4.2, 4.3.3 |
| 2. จำกัดเฉพาะคนในคณะ และคุ้มครองข้อมูลตาม PDPA | **[เติม]** | หัวข้อ 4.3.2 |
| 3. คัดกรองก่อนเผยแพร่ ข้อสอบคุมเข้ม ตรวจย้อนหลังได้ | **[เติม]** | หัวข้อ 4.2, 4.3.2 |
| 4. ประยุกต์ Scrum, Modular Monolith, Service Layer, 3NF | **[เติม]** | หัวข้อ 4.1, 4.5 |

## 5.2 อภิปรายผล

ประเด็นที่มีข้อมูลรองรับอยู่แล้วและควรอภิปราย (เติมผลจริงให้ครบ):

1. **การเปลี่ยนจาก SRS เป็น Agile Backlog** — ข้อดี (ปรับลำดับได้ทุก Sprint, ไม่เสียเวลาลงรายละเอียด story ที่อาจไม่ได้ทำ) เทียบกับข้อเสีย (ทีมต้องคุยกฎธุรกิจซ้ำก่อนทุก Sprint, เอกสารกระจายระหว่าง repo กับ GitHub issue) **[เติม: สิ่งที่เกิดขึ้นจริง]**
2. **Modular Monolith กับการทำงานขนาน** — ADR 0001 คาดว่าจะลด merge conflict เพราะแบ่งงานตาม app ได้ **[เติม: จำนวน conflict / ปัญหา circular import ที่เจอจริง]**
3. **Service Layer กับการทดสอบ** — ADR 0002 คาดว่าทดสอบกฎธุรกิจได้โดยไม่ผ่าน HTTP **[เติม: coverage ของ services.py เทียบ views.py, ความยากง่ายที่ทีมรู้สึก]**
4. **เก็บกฎเป็นข้อมูล (`doc_type_required_role`, `system_setting`)** — ยืดหยุ่นแต่เพิ่มความซับซ้อน (เช่น ต้องเพิ่ม column `mode` = any/all ถ้าจะเก็บกฎ "อย่างใดอย่างหนึ่ง" ในข้อมูลทั้งหมด)
5. **การบังคับกฎหลายชั้น (DB / Model / Service)** — กฎที่ฐานข้อมูลบังคับไม่ได้ (เช่น partial unique index บน MySQL) ต้องเขียนซ้ำใน model
6. **Velocity และความแม่นยำของการประมาณ** — เปรียบเทียบแต้มที่วางแผนกับที่เสร็จจริงระหว่าง Sprint **[เติม]**
7. **การใช้ AI ช่วยพัฒนา** — ผลของกติกา "ผู้ commit รับผิดชอบ 100% และต้องอธิบายโค้ดได้" **[เติม]**

## 5.4 ข้อเสนอแนะและงานในอนาคต

นำ story/spike ที่ยังไม่ได้ทำจาก [`requirements.md`](../requirements.md) มาเป็นงานในอนาคต **[ตรวจ: ตัดรายการที่ทำเสร็จแล้วออก]**

- **E1:** ยืนยันอีเมลด้วยลิงก์/OTP (US-11), ผูกอีเมลส่วนตัวสำหรับศิษย์เก่า (US-12), ลบบัญชีตาม PDPA (US-13), ระงับผู้ใช้ (US-14)
- **E2:** นำเข้าข้อมูลเดิมด้วย CSV พร้อม dry run (US-15), ขยายไปภาควิชาอื่นพร้อมกฎเลขรุ่น (US-18)
- **E3:** ส่งเวอร์ชันใหม่/แก้ไข/ลบไฟล์ (US-19), แท็ก (US-20), ตรวจไฟล์ซ้ำและไวรัส (US-21)
- **E4:** Audit Log หน้าจอ (US-24)
- **E5:** กรองผลค้นหาตามปีการศึกษา/ช่วงสอบ และเรียงผลค้นหา (US-26, US-27) — การกรองภาค/รุ่น/ประเภท และ preview PDF ในเว็บ (SP-3) ทำแล้วใน US-7
- **E6:** คอมเมนต์ ให้คะแนน และปักหมุด (US-28 – US-30)
- **E7:** ระบบรายงานปัญหาและแบบฟอร์มแจ้งลบเนื้อหาสาธารณะ (US-31 – US-33)
- ด้านเทคนิค: ค้นหาแบบ full-text (เช่น PostgreSQL full-text search), cache ยอดดาวน์โหลดเมื่อข้อมูลโต, ระบบสำรองข้อมูลอัตโนมัติ
