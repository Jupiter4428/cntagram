## 1.1 ที่มาและความสำคัญ

นักศึกษาคณะวิศวกรรมศาสตร์ใช้ชีทสรุป สไลด์บรรยาย ชีทสูตร และข้อสอบเก่าเป็นสื่อทบทวนสำคัญ เอกสารเหล่านี้ส่วนใหญ่ถูกส่งต่อจากรุ่นพี่สู่รุ่นน้องผ่านกลุ่มแชทและไดรฟ์ส่วนตัว ซึ่งก่อให้เกิดปัญหาดังนี้

1. **ค้นหายาก** เอกสารของวิชาเดียวกันกระจายอยู่หลายกลุ่มและหลายรุ่น ต้องไล่ถามหรือเลื่อนหาในแชท
2. **ไม่มีการคัดกรองคุณภาพ** ไม่มีใครตรวจว่าเอกสารถูกต้อง ครบถ้วน หรือเป็นของวิชา/ปีที่ระบุจริง
3. **ความรู้ขาดช่วง** เมื่อรุ่นพี่จบการศึกษาและอีเมลมหาวิทยาลัยถูกปิด ไฟล์ในไดรฟ์ส่วนตัวมักหายไปด้วย
4. **ความเสี่ยงด้านลิขสิทธิ์และข้อมูลส่วนบุคคล** ไม่มีช่องทางให้อาจารย์หรือเจ้าของลิขสิทธิ์แจ้งลบเนื้อหา และไม่มีการควบคุมการเข้าถึงหรือการเปิดเผยข้อมูลผู้ใช้

**[เติม: หลักฐานเชิงประจักษ์ของปัญหา เช่น ผลสำรวจสั้นๆ จากนักศึกษา CN จำนวนกลุ่มแชท/ไดรฟ์ที่ใช้อยู่ หรือคำสัมภาษณ์ — ช่วยให้บทนี้น่าเชื่อถือขึ้นมาก]**

จากปัญหาดังกล่าว ผู้จัดทำจึงพัฒนาระบบ **CNtagram** เว็บบอร์ดคลังเอกสารกลางที่ให้นักศึกษาวิศวะทุกภาควิชา "หาชีทสรุปและข้อสอบเก่าของวิชาที่ต้องการเจอได้ในที่เดียว" โดยเอกสารผ่านการคัดกรองก่อนเผยแพร่ เข้าถึงได้เฉพาะคนในคณะ และเคารพลิขสิทธิ์ของอาจารย์ ระบบนี้พัฒนาเป็นโครงงานของรายวิชา CN331 Software Engineering ตามกระบวนการ Scrum จึงเป็นทั้งการแก้ปัญหาจริงและการประยุกต์หลักวิศวกรรมซอฟต์แวร์ตลอดวงจรการพัฒนา

## 1.2 วัตถุประสงค์

1. เพื่อพัฒนาเว็บแอปพลิเคชันคลังชีทสรุปและข้อสอบเก่าที่จัดเอกสารตามลำดับชั้น ภาควิชา → รุ่น → รายวิชา และค้นหาด้วยรหัสวิชาได้จากทุกรุ่นในหน้าเดียว
2. เพื่อจำกัดการเข้าถึงเฉพาะนักศึกษาและศิษย์เก่าของคณะวิศวกรรมศาสตร์ และคุ้มครองข้อมูลส่วนบุคคลของผู้ใช้ตาม PDPA
3. เพื่อสร้างกระบวนการคัดกรองเอกสารก่อนเผยแพร่ โดยข้อสอบเก่าถูกควบคุมเข้มกว่าเอกสารทั่วไป และตรวจสอบย้อนหลังได้
4. เพื่อประยุกต์กระบวนการ Scrum และหลักการออกแบบสถาปัตยกรรมซอฟต์แวร์ (Modular Monolith, Service Layer, ADR) และการออกแบบฐานข้อมูลเชิงสัมพันธ์ (3NF) ในการพัฒนาระบบจริง

## 1.3 ขอบเขตของโครงงาน

### 1.3.1 ขอบเขตด้านผู้ใช้

| บทบาท | ความสามารถหลัก |
|---|---|
| Guest | ดูหน้าแนะนำ สมัครสมาชิก และเข้าสู่ระบบ (ไม่เห็นเอกสารในคลัง) |
| Student | ค้นหา อ่าน ดาวน์โหลด และอัปโหลดเอกสาร |
| Alumni | ใช้งานคลังต่อหลังจบการศึกษาผ่านอีเมลส่วนตัวที่ผูกไว้ |
| Moderator | คัดกรองเอกสารของภาควิชาที่ได้รับแต่งตั้ง |
| Super Admin | ดูแลโครงสร้างข้อมูล สิทธิ์ ข้อสอบรุ่นเก่า และเรื่องลิขสิทธิ์ |

### 1.3.2 ขอบเขตด้านข้อมูล
- เริ่มต้นกับภาควิชาวิศวกรรมคอมพิวเตอร์ (CN) ข้อมูลรุ่น CN21–CN25 และออกแบบให้ขยายไปภาควิชาอื่นได้โดยไม่แก้โค้ด
- เอกสารเป็นไฟล์ PDF แบ่งเป็น 2 คลัง: **คลัง Lecture/ชีทสรุป** (ผูกกับรุ่น) และ **คลังข้อสอบเก่า** (รวมศูนย์ตามรายวิชา ระบุช่วงสอบและปี พ.ศ.)

### 1.3.3 ขอบเขตด้านฟังก์ชัน (ตาม Epic)
E1 เข้าระบบอย่างปลอดภัย · E2 โครงสร้างคลัง · E3 แบ่งปันเอกสาร · E4 คัดกรองคุณภาพ · E5 ค้นหาและอ่าน · E6 ชุมชน · E7 ลิขสิทธิ์และความไว้วางใจ (รายละเอียดในบทที่ 3 หัวข้อ 3.2)

> **[ตรวจ: ก่อนส่งเล่ม ปรับขอบเขตให้ตรงกับสิ่งที่ส่งมอบจริง]** ใน Agile ขอบเขตเปลี่ยนได้ทุก Sprint ให้ระบุว่า Epic/Story ใด "ส่งมอบแล้ว" และใดอยู่ใน "งานในอนาคต" (บทที่ 5) แทนการเขียนว่าระบบทำได้ทุกข้อ

### 1.3.4 ข้อจำกัด
- พัฒนาด้วย Python 3.12+ และ Django บนฐานข้อมูลเชิงสัมพันธ์ จัดการงานบน GitHub (Issues, Projects, Pull Request) และสาธิตระบบในสัปดาห์ที่ 14 ของภาคการศึกษา
- ยืนยันตัวตนด้วยอีเมล `@student.tu.ac.th` และหลักที่ 3–4 ของรหัสนักศึกษาต้องเป็น `10` (คณะวิศวกรรมศาสตร์)
- ต้องสอดคล้องกับ PDPA (ขอความยินยอม ไม่แสดงอีเมลต่อผู้อื่น ลบ/ปิดบังข้อมูลได้เมื่อร้องขอ) และมีช่องทางแจ้งลบเนื้อหาที่ละเมิดลิขสิทธิ์
- ทีมพัฒนา 5 คน ระยะเวลา 3 Sprint

## 1.4 ประโยชน์ที่คาดว่าจะได้รับ

1. นักศึกษาค้นหาเอกสารของรายวิชาได้รวดเร็ว (เป้าหมายเริ่มต้นประมาณ 2 วินาที และไม่เกิน 2 คลิกจากผลค้นหาถึงไฟล์)
2. คลังเอกสารมีคุณภาพเพราะผ่านการคัดกรอง และความรู้ส่งต่อระหว่างรุ่นได้ต่อเนื่อง
3. คณะมีกลไกจัดการลิขสิทธิ์และข้อมูลส่วนบุคคลที่ตรวจสอบย้อนหลังได้
4. ผู้จัดทำได้ประสบการณ์พัฒนาซอฟต์แวร์เป็นทีมตามกระบวนการ Scrum และหลักวิศวกรรมซอฟต์แวร์ที่ใช้ในอุตสาหกรรม

## 1.5 นิยามศัพท์เฉพาะ

| คำศัพท์ | ความหมายในโครงงานนี้ |
|---|---|
| รุ่น (Batch) | กลุ่มนักศึกษาที่เข้าภาควิชาในปีเดียวกัน แสดงผลเป็นรหัสภาค + เลขรุ่น เช่น CN21 |
| คลัง (Vault) | กลุ่มการจัดเก็บเอกสาร มี 2 แบบคือ `lecture` (แยกตามรุ่น) และ `exam` (ข้อสอบรวมข้ามรุ่น) |
| Moderator | ตัวแทนนักศึกษาประจำภาควิชาที่ได้รับแต่งตั้งให้คัดกรองเอกสารของภาค |
| Super Admin | ผู้ดูแลระบบส่วนกลางของคณะ |
| User Story | ความต้องการที่เขียนจากมุมผู้ใช้ในรูปแบบ "As a … I want … so that …" |
| Story Point | หน่วยประมาณขนาดงานเชิงสัมพัทธ์ที่ทีมตกลงร่วมกัน |
| Velocity | จำนวน Story Points ที่ทีมส่งมอบได้ (ผ่าน DoD) ต่อ Sprint |
| DoR / DoD | Definition of Ready / Definition of Done เกณฑ์ก่อนดึงงานเข้า Sprint และก่อนนับว่างานเสร็จ |
| ADR | Architectural Decision Record บันทึกเหตุผลของการตัดสินใจเชิงสถาปัตยกรรม |
| PDPA | พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 |
